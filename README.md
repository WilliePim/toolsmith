*[Italiano](README.it.md) · English*

**An agent that writes, checks and reuses its own Python tools — and a measurement
harness that says how much that is actually worth.**

When a task applies one rule across many inputs, the agent stops working it out in the
conversation and writes a small program instead. That program is checked, sandboxed,
saved to disk, and available as a tool from the very next round.

```
$ uv run python -m src.main run gstin_1
────────────────── gstin_1  (GSTIN check character) ──────────────────
  r2 write_tool 'gstin_check_char': registered
  r3 gstin_check_char(prefix='16TEUYJ4263R1Z') -> 'K'
  r3 gstin_check_char(prefix='14ELRKY8914Q4Z') -> 'X'
  r3 gstin_check_char(prefix='03ZPVMA6122X3Z') -> 'M'
  r3 gstin_check_char(prefix='07RJXDS8075B1Z') -> 'S'
  r4 submit_answer -> 'KXMS' correct
```

## How it works

The agent starts with the toolbox a generic assistant ships with: a calculator and
today's date. They are deliberately *almost* right — a checksum is arithmetic, an ISO
week label is a date — and neither actually solves its task, because `calc` evaluates
one expression per round. That gap is what turns "write a tool" into a decision rather
than a scripted step.

A tool the model writes passes four gates before it can be called:

| Gate | What it does | Cost of a refusal |
|---|---|---|
| **1. Spec check** | the tool must take the family's exact parameters, with at least two tests | one repair turn |
| **2. Static guard** | reads the source as an AST and refuses unsafe names, imports and constructs | one repair turn |
| **3. Sandbox** | runs it in an isolated subprocess against the model's tests **and against inputs the model never sees** | one repair turn |
| **4. Registry** | saves it as `generated/<name>.py` + `.json`, re-checked on every load | — |

Gate 3 is the interesting one: a tool that passes its own tests can still be subtly
wrong, and the held-out check exists to catch exactly that. The model is told only *how
many* hidden batches failed, plus a hint — never the inputs, the expected values, or an
exception message that could echo one back.

Then **the one line**: the tools array is rebuilt *inside* the round loop, so a tool
written in round *N* is callable in round *N+1*, mid-conversation.

Diagrams and module-by-module detail: [docs/en/architecture.md](docs/en/architecture.md).

## Security, measured

Both layers are proven by an adversarial suite that needs **no API key**:

```bash
uv run python -m src.redteam --json results/sandbox_$(uname -s).json
```

Attacks cover reading outside the allowed directory, writing to disk, network access,
spawning processes, infinite loops, excessive memory, forbidden imports, interpreter
escapes, and swallowing the sandbox's own violation. Runtime attacks are sent **past the
guard on purpose**, to prove the audit hook holds alone.

<!-- GENERATED:sandbox:START -->
| platform | memory cap | attacks | contained | by the guard | by the sandbox | documented limits | undeclared escapes |
|---|---|---|---|---|---|---|---|
| Linux | RLIMIT_AS 1 GB | 42 | 42/42 | 27 | 15 | - | none |
| Windows | none (Windows: only the watchdog timeout) | 42 | 41/42 | 27 | 14 | memory bomb (4 GB) | none |
<!-- GENERATED:sandbox:END -->

**One attack is not contained on Windows, and it is reported rather than quietly
patched.** A single 4 GB allocation succeeds there: Windows has no address-space cap and
the allocation finishes inside the watchdog's timeout. The Linux row is not a prediction
— it is the same suite run in CI, where the sandbox's `RLIMIT_AS` turns that attack into
a `MemoryError` and all 42 are contained. Deploying on Linux or in a container closes
this gap. The suite fails on any *undeclared* escape; a documented limit is reported
instead, so the signal stays meaningful. Details and other limits:
[docs/en/security.md](docs/en/security.md).

## Quickstart

Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```bash
uv sync
cp .env.example .env          # paste a free Gemini key from aistudio.google.com/apikey
```

```bash
uv run python -m src.main redteam      # both security layers, no API key needed
uv run python -m src.main run gstin_1  # solve one task
uv run python -m src.main run --all --set finance
uv run python -m src.main tools        # what the agent has written
uv run python -m src.main show gstin_check_char
```

Set `PROVIDER=claude` and `ANTHROPIC_API_KEY` to run on Claude instead; the adapter is
written and offline-tested, and the model layer is provider-neutral.

## The tasks

Two sets, each with two families, each family with two tasks so the second reuses the
first's tool. Each family hides an edge case in its held-out inputs only.

| Set | Family | Rule | Hidden edge case |
|---|---|---|---|
| `core` | GSTIN check character | base-36 checksum over 14 characters | a check character that is a digit, not a letter |
| `core` | ISO week label | `YYYY-Www-D` from a date | a date whose ISO week belongs to the neighbouring year |
| `finance` | ISIN check digit | letters → digits, then Luhn | letters in the body shift the Luhn doubling |
| `finance` | trading session | the nth session after a date | a market holiday inside the range |

Both task files are **generated from reference code**, never typed: `src/taskgen.py` and
`src/taskgen_finance.py`, the latter cross-checked against `python-stdnum` and
`exchange-calendars`. `--check` proves the committed file still matches its generator.
Why these families, and how to add your own: [docs/en/task-sets.md](docs/en/task-sets.md).

## Method

The comparison is only worth reading if the baseline is fair. **Baseline** is the same
model, the same tasks and the same system prompt with *only* the tool-writing lines
removed — a prompt describing a tool the condition cannot use would handicap it rather
than measure it.

Each repetition starts from an **empty, isolated toolbox**, so "the first task writes,
the second reuses" stays what is being measured. Provider failures (429, 5xx, network)
are retried with growing backoff and counted separately; everything the agent itself did
— a wrong answer, a refused tool, running out of rounds — is recorded as it happened.
Every run stores the model, temperature, prompt hash and code commit. The runner is
resumable, so a spent daily quota can be waited out.

### Where the four gates actually fired

<!-- GENERATED:bench-refusals:START -->
| gate that refused a tool | times |
|---|---|
| the model's own tests, run in the sandbox | 3 |
| the spec check (too few or malformed tests) | 2 |

45 tool-writing attempts in total; 5 were refused and 3 run(s) went on to register a repaired tool.

Counting every run on disk, including the extra ones made hunting for one: **0 held-out rejections** across 60 tool-writing attempts, on 2 model(s) (gemini-3.1-flash-lite, gemini-3.8-flash).
<!-- GENERATED:bench-refusals:END -->

Read that strictly: the refusals came from the model's *own* tests and from the spec
check. **The held-out check ran on every registration and rejected nothing**, and that
zero is worth explaining rather than leaving as a gap.

I went looking for a rejection: eight further runs of `isoweek_1` on the weakest model
the account exposes (`gemini-3.1-flash-lite`), each from an empty toolbox. It refused
tools at the guard, the spec check and its own tests — and never at the held-out check.
The reason is visible in what it wrote: **all eight tools call `isocalendar()` and take
the ISO year from it.** The trap was built for `f"{d.year}-W{week}"`, which uses the
*calendar* year; but Python's standard library returns the ISO year as the first element,
so any model reaching for the obvious function is correct by construction. The same holds
for the other three families: `int(c, 36)` gets ISIN letters right, an alphabet string
gets GSTIN digits right, and a tool handed a holiday list uses it.

The honest conclusion: for these four rules the idiomatic Python solution *is* the correct
one, so the held-out check is a net that a capable model rarely falls into. It catches a
hand-rolled implementation — which is exactly what `uv run python -m src.smith`
demonstrates, building a deliberately wrong GSTIN tool that passes its own tests and
watching the held-out check reject it with only a count and a hint. **A family where the
obvious solution is subtly wrong would exercise this gate far harder, and that is the
clearest thing to build next.**

## What comes from the reference, and what is new here

The project follows a paid tutorial on building a self-extending agent, whose second half
was behind a paywall and which is therefore not linked or redistributed here. Nothing
from it is reproduced: no text, figures or tables — only a description, in my own words,
of which ideas came from the readable half and which were designed for this repository.

**From the reference, re-implemented:** the overall shape — rebuilding the tool list
inside the round loop, splitting safety into a static pass and a sandboxed run, checking
a generated tool against inputs the model cannot see, keeping tools as plain files, and
starting from two deliberately almost-relevant tools. The GSTIN family and its worked
example come from there; the task file is regenerated from a reference implementation
because the reference's own sample answer for a hidden input did not check out.

**New here:** every module after the halfway point — the sandbox runner and its watchdog,
the static guard, the registry, the write-check-register gauntlet, the prompts, the agent
loop, the red-team corpus and the CLI. Beyond that: a provider-neutral model layer with
Gemini and Claude adapters; a per-run nonce so a tool cannot forge its own results;
preloading modules so the audit hook does not break ordinary imports; path normalisation
in the file-open rule; a per-family tool interface that lets the held-out check call a
tool with hidden inputs; a second task set cross-checked against external libraries; and
the whole measurement harness this README's numbers come from.

## Layout

```
src/
  config.py             every setting in one place
  tools.py              the two starting tools
  llm.py + providers/   one door to Gemini or Claude; never raises
  protocol.py           preamble + source + footer, and result parsing
  sandbox.py            the locked-down subprocess and its watchdog
  guard.py              the static AST layer
  registry.py           the toolbox that grows, as files
  smith.py              write, check, register
  tasks.py, prompts.py  typed tasks, and what the model is told
  agent.py              the round loop and the one line
  attacks.py, redteam.py  the adversarial proof
  taskgen*.py           build the task files from reference code
  bench.py, report.py   the measurement harness behind every number here
  main.py               the command line
results/                run records, toolboxes, prompts, summary.json
docs/{en,it}/           architecture, security, task sets, design, build journal
```

Every module has a `__main__` self-check: `uv run python -m src.<module>`.
CI runs them, both task generators and the red-team suite on Linux.

**If you only read three files:** [`src/guard.py`](src/guard.py) for the default-deny
AST layer and why each rule exists, [`src/smith.py`](src/smith.py) for the
write-check-register gauntlet and the rule that a held-out failure reveals only a count
and a hint, and [`src/bench.py`](src/bench.py) for how the measurements avoid fooling
themselves.

## Safety note

The sandbox denies OS, filesystem and network access through a Python audit hook and runs
each tool in an isolated subprocess with a scrubbed environment (no API keys), a timeout
and an output cap; on POSIX it also sets hard CPU and memory limits. It is a strong
barrier for a demo, not a claim of perfect isolation — see the measured limit above. Do
not point it at untrusted input on a machine you cannot afford to lose.
