# toolsmith

*[Italiano](README.it.md) · English*

An agent that starts with two tools — a calculator and today's date — and **writes a third when it meets a task the first two cannot do**. The tool it writes is an ordinary Python file on disk; the next task of the same kind calls it instead of writing it again.

A tool the model writes goes through four gates before it can be called:

1. a **static guard** reads the source and either refuses it with a reason or lets it through;
2. a **sandbox** runs it in a locked-down subprocess, against the model's own tests *and* against inputs it has never seen;
3. a **registry** saves a tool that passes as `generated/<name>.py`;
4. the saved tool joins the model's tool list **the very next round**, mid-conversation.

> ### What this is, and what it is not
>
> This is a **demonstration of a mechanism, not a benchmark.** It runs 8 tasks in 4
> families. That is enough to show that the loop, the guard, the sandbox and the
> reuse work, and nowhere near enough to make a general claim about agents, models
> or task types. The numbers below come from repeated runs of those 8 tasks only.
>
> Every figure in this file is generated by `src/report.py` from the run files in
> `results/`. None of them is typed by hand. Reproduce them with one command:
> `uv run python -m src.bench --repeats 10 && uv run python -m src.report`.

## Does writing tools actually help?

The honest way to answer is to run the same tasks many times, in two conditions,
and report the spread rather than a lucky run.

**With tools** the agent may write, register and call tools. **Baseline** is the same
model, the same tasks and the same prompt *minus the lines about writing tools* — a
prompt that described a tool the condition cannot use would handicap it, not measure it.

<!-- GENERATED:prompt-diff:START -->
Only the tool-writing lines are removed; the opening and the closing instruction are byte-identical in both conditions.

@@ -2,11 +2,2 @@

-
-When you write a tool, follow this contract exactly:
-- Define one function, run(...), taking exactly the parameters the task states, and returning a string.

## The sandbox, measured

`src/attacks.py` holds hostile tools in the categories below; `src/redteam.py` runs
each one and records which layer stopped it. Attacks aimed at the runtime are sent
**past the guard on purpose**, to prove the audit hook holds on its own. No API calls
are involved, so anyone can reproduce this in seconds:

```bash
uv run python -m src.redteam --json results/sandbox_$(uname -s).json
```

Categories covered: reading outside the allowed directory, writing to disk, network
access, spawning processes, infinite loops, excessive memory, forbidden module
imports, interpreter escapes, and swallowing the sandbox's own violation.

<!-- GENERATED:sandbox:START -->
| platform | memory cap | attacks | contained | by the guard | by the sandbox | documented limits | undeclared escapes |
|---|---|---|---|---|---|---|---|
| Windows | none (Windows: only the watchdog timeout) | 42 | 41/42 | 27 | 14 | memory bomb (4 GB) | none |
<!-- GENERATED:sandbox:END -->

**A documented limit, not a fixed one.** On Windows a single 4 GB allocation is *not*
contained: there is no address-space cap, and the allocation finishes well inside the
watchdog's timeout. On Linux the sandbox sets `RLIMIT_AS`, so the same attack is
refused. This is reported rather than quietly patched, because a suite that hides its
misses is worth nothing.

## Quickstart

You need [Python 3.12+](https://www.python.org/) and [uv](https://docs.astral.sh/uv/).

```bash
uv sync                              # install the locked dependencies
cp .env.example .env                 # then paste a free Gemini key into .env
```

A free Gemini API key comes from [aistudio.google.com/apikey](https://aistudio.google.com/apikey). Paste it into `.env` as `GEMINI_API_KEY=...`. To use Claude instead, set `PROVIDER=claude` and `ANTHROPIC_API_KEY=...` (billed per use; a Claude.ai subscription is not API access).

```bash
uv run python -m src.main redteam            # prove both security layers — no API key needed
uv run python -m src.main run gstin_1        # solve one task
uv run python -m src.main run --all          # the whole core set
uv run python -m src.main run --all --set finance
uv run python -m src.main tools              # list the tools the agent has written
uv run python -m src.main show gstin_check_char
uv run python -m src.main reset              # empty the toolbox
```

Reproduce the measurements (this spends API quota, and resumes if it is interrupted):

```bash
uv run python -m src.bench --repeats 10      # every task, both conditions
uv run python -m src.report                  # regenerate every table above
```

## The tasks

Two task **sets**, each with two **families**, each family with two tasks so the second
reuses the first's tool. The families are chosen to force each part of the machinery;
see [docs/en/task-sets.md](docs/en/task-sets.md).

| Set | Family | The rule | The hidden edge case |
|---|---|---|---|
| `core` | GSTIN check character | a base-36 checksum over 14 characters | a check character that is a digit, not a letter |
| `core` | ISO week label | `YYYY-Www-D` from a date | a date whose ISO week belongs to the neighbouring year |
| `finance` | ISIN check digit | letters → digits, then Luhn | letters in the body shift the Luhn doubling |
| `finance` | trading session | the nth session after a date | a market holiday inside the range |

Every task file is generated from reference code (`src/taskgen.py`, `src/taskgen_finance.py`); the finance answers are cross-checked against `python-stdnum` and `exchange-calendars`.

## What comes from the reference, and what is new here

The project follows a tutorial on building a self-extending agent, whose second half
was behind a paywall. *Reference: (placeholder — to be filled in).* Nothing from it is
reproduced here: no text, figures or tables. What follows is a description in my own
words of which ideas came from the readable half, and which were designed for this
repository.

**From the reference (ideas, re-implemented):** the overall shape — an agent whose tool
list is rebuilt inside the round loop; splitting safety into a static pass over the
source and a sandboxed run; checking a generated tool against inputs the model cannot
see; keeping tools as plain files so they outlive the conversation; and the two starting
tools being deliberately almost-relevant. The GSTIN family and its worked example come
from the reference; the task file here is regenerated from a reference implementation
because the reference's own sample answer for a hidden input did not check out.

**New here:** every module after the halfway point was designed from scratch — the
sandbox runner and its watchdog, the static guard, the registry, the write-check-register
gauntlet, the prompts, the agent loop, the red-team corpus and the CLI. Beyond that:
a provider-neutral model layer with Gemini and Claude adapters replacing the reference's
single provider; a per-run nonce so a tool cannot forge its own results; preloading
modules so the audit hook does not break ordinary imports; path normalisation in the
file-open rule; a per-family tool interface that lets the held-out check call a tool
with hidden inputs; a second task set cross-checked against external libraries; and the
whole measurement harness this README's numbers come from.

## Safety note

The sandbox denies OS, filesystem and network access via a Python audit hook, and runs
each tool in an isolated subprocess with a scrubbed environment (no API keys), a timeout
and an output cap. On POSIX it also sets hard CPU and memory limits; on Windows, memory
is bounded only by the timeout — see the measured limit above. It is a strong barrier
for a demo, not a claim of perfect isolation. Do not point this at untrusted input on a
machine you cannot afford to lose. See [docs/en/security.md](docs/en/security.md).
